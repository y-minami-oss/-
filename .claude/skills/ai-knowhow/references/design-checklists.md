# 設計チェックリスト

## A. RAG/MCP で業務自動化を設計するとき

PoC 止まりを避けるための順序。上から順に守る。

- [ ] **測れる高インパクトな1ユースケースから始める。** 実際に収益が出ている用途は
      コーディング支援 > サポート自動化 > 社内ナレッジ検索 の順(a16z調査)。
      「全社導入」から始めない。
- [ ] **ツールは最小の面をよく作る。** 雑な50個より良い5個。MCP の設計指針でもある。
- [ ] **全部をRAGに入れない。** いつ・何を取得するかをモデルに判断させる
      (agentic RAG)。無関係な取得が減る一方、retrieval ループという新しい失敗が出る。
- [ ] **使い分ける**: 変化しない情報(evergreen)は RAG で索引、
      トランザクション系のライブ参照は MCP。
- [ ] hybrid retrieval をベースラインにする。
- [ ] **権限は最小に絞る。** 最初から広い権限を渡さない。
- [ ] **テレメトリを集める**(ログ・フィードバック)。測れないものは改善できない。
- [ ] **コアが安定してから拡張する。**

判定: この順序自体はこのセッションで実証していないが、
「権限最小」「最小のツール面」「計測から始める」は
自動化の設計原則として妥当で、このリポジトリの `draft_only: true` 既定
(最終申請まで自動化しない)と同じ発想。

## B. AI生成物を商用で使う / 納品する前

- [ ] 生成物が**既存の特定作品に実質的に類似していないか**確認。
      米国の訴訟の争点は「学習元データ」から「生成物が既存作品に似ているか」へ移った。
      利用者側の現実的な防衛線はここ。
- [ ] 特定クリエイターの**作風に過度依存したプロンプトになっていないか**。
      日本の文化庁の整理では、学習データ利用は原則許諾不要だが
      「著作権者の利益を不当に害す場合」は侵害とされる。基準が曖昧なので余裕を持つ。
- [ ] 使用ツールの**商用ライセンス・クレジット表記・透かし要件**を満たしているか。
      例: Nano Banana Pro は商用可だが全画像に SynthID 透かしが入る。
- [ ] **学習・生成の用途を記録**(どの素材をどう使ったか)。争いになったとき唯一の武器。
- [ ] EU向けなら **EU AI Act のハイリスク該当性**を棚卸し。
- [ ] 国内は **AI事業者ガイドライン**に沿った自主ガバナンスを社内規程に反映。
      日本は罰則型でないため、体制整備そのものが取引上の差別化になる。

> ⚠️ 法令の施行日・制裁金額・条文解釈は DB 収集時点(2026年6月)の転記。
> 実際の判断は必ず一次情報か専門家に当たること。ここは判断材料であって法的助言ではない。
