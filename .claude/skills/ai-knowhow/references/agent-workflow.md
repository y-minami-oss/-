# コーディングエージェントを自走させる

公式ドキュメント(https://code.claude.com/docs/en/best-practices)と照合済み。
DB の元記述に足りなかった但し書きは「⚠️ 補足」として追記した。

## 根拠(全ての土台)

> Most best practices are based on one constraint: Claude's context window fills up
> fast, and performance degrades as it fills.

「文脈窓が埋まると性能が落ちる」——以下の手順は全てこれに帰着する。

## 5手順

### ① Explore — 調査だけをさせる(実装させない)
plan mode(`Shift+Tab` で `⏸ plan mode on`、または `claude --permission-mode plan`)に入り、
ファイルを読ませて現状を把握させる。大量のファイルを読む調査は subagent に逃がし、本文脈を汚さない。

### ② Plan — 計画を出させ、実装と分離してレビュー
`Ctrl+G` で計画をエディタで直接編集できる。

> ⚠️ **補足(公式にあり、DBに無かった点)**: plan mode はオーバーヘッドでもある。
> スコープが明確で修正が小さいとき(typo・ログ追加・変数名変更)は直接やらせる。
> **「差分を1文で説明できるなら計画は飛ばす」**が判断基準。
> 計画が効くのは、方針が不確か / 複数ファイルに触る / 対象コードに不慣れなとき。

### ③ Implement — 検証手段を必ず与えてから実装させる

> Claude stops when the work looks done. Without a check it can run, "looks done"
> is the only signal available, and you become the verification loop.

検証手段 = pass/fail を返すもの。テストスイート、ビルドの終了コード、リンター、
出力をフィクスチャと比較するスクリプト、スクリーンショット比較。

悪い例 → 良い例:
- 「メールアドレスを検証する関数を実装して」
  → 「validateEmail を書いて。テストケース: `user@example.com` は true、`invalid` は false、
    `user@.com` は false。実装後にテストを走らせて」
- 「ビルドが失敗する」
  → 「ビルドがこのエラーで失敗する: [貼付]。直してビルド成功を確認して。
    エラーを抑制せず根本原因に対処して」

止め方の強度は3段階で選べる(公式、DBに無かった):

| 手段 | 効き方 |
|---|---|
| プロンプト内で指示 | 今日から使える。同じメッセージで「検証して直るまで繰り返して」 |
| `/goal` 条件 | 別の評価器が毎ターン再チェックし、条件が解けるまで作業継続 |
| Stop hook | スクリプトで検証し、通るまでターン終了をブロック(決定的) |

**成功を主張させず、証拠を出させる。** テスト出力、実行したコマンドとその戻り値、
スクリーンショット。証拠を読むほうが自分で再実行するより速い。

### ④ Review — 完了前に「diffだけ見る」敵対レビューを挟む
新しい文脈の subagent は、その変更を生んだ推論を知らないので、結果だけで評価できる。
バグ検出なら `/code-review` スキル。計画との突合なら自分でプロンプトを書く:

```
Use a subagent to review the {対象} diff against PLAN.md. Check that every
requirement is implemented, the listed edge cases have tests, and nothing
outside the task's scope changed. Report gaps, not style preferences.
```

> ⚠️ **補足(公式にあり、DBに無かった点)**: 「不備を探せ」と指示されたレビュアーは、
> 健全な変更でも何かしら報告する。全部追うと過剰設計(不要な抽象化・防御的コード・
> 起こり得ないケースのテスト)になる。**「正しさか明示要件に影響する不備だけ挙げろ」**
> と指示し、残りは任意扱いにする。

### ⑤ Commit / Clear
コミット後、無関係なタスクに移る前に `/clear` で文脈をリセット。

## よくある失敗(公式より)

| 失敗 | 直し方 |
|---|---|
| 1セッションに無関係な話題を混ぜる | タスク間で `/clear` |
| 同じ点を何度も修正させる | 2回失敗したら `/clear` して、学んだことを織り込んだ指示で作り直す |
| CLAUDE.md が長すぎる | 容赦なく削る。指示なしで正しくできることは消す |
| 妥当そうだが穴のある実装を信じる | 常に検証手段を用意する。検証できないものは出さない |
| スコープなしの「調査して」 | 範囲を狭める、または subagent に逃がす |

## CLAUDE.md の書き方

各行に **「消したらClaudeが間違えるか?」** を問い、否なら削る。
`/context` で読み込まれたか確認できる。

| ✅ 書く | ❌ 書かない |
|---|---|
| 推測できないコマンド | コードを読めば分かること |
| 既定と違うコードスタイル規約 | 言語の標準的な慣習 |
| テスト手順・使うテストランナー | 詳細なAPI仕様(リンクにする) |
| リポジトリの作法(ブランチ名・PR規約) | 頻繁に変わる情報 |
| このプロジェクト固有の設計判断 | 長い説明・チュートリアル |
| 環境の癖(必要な環境変数) | ファイルごとの説明 |
| 非自明な落とし穴 | 「きれいなコードを書く」等の自明な話 |

**「たまにしか関係しない領域知識やワークフローは CLAUDE.md ではなくスキルに置く」**
(公式)。だからこのノウハウ集自体もスキルにしている。

## マルチエージェント(subagent 並列)を使う判断

lead agent が分解して専門 subagent を並列起動する構成は、単一エージェントより
大幅に性能が上がる一方、**通常のチャット比で約15倍のトークンを消費する**(Anthropic公式)。

- 向く: 並列に調べられる調査タスク。
- 向かない: 密結合なコーディング(subagent 間で文脈を共有できない)。
- 判断軸: **「価値がコストを上回る並列タスク」に限定する。** 万能ではない。
